# DomBeacon Overview

For the docs index, see [README.md](README.md). For a feature-by-feature
reference, see [features.md](features.md).

## Product Positioning

DomBeacon is a self-hosted domain ops beacon for tracking wanted domain
opportunities, managing owned domain portfolios, monitoring expiry/SSL/DNS
risks, and detecting brand-abuse candidates through public RDAP and
Certificate Transparency signals.

Designed for:

- Individual domain investors tracking opportunities.
- Small teams managing owned domain portfolios.
- Internal security or platform teams monitoring domain attack surface.
- Self-hosted setups that do not want a mandatory SaaS dependency.

## Core Concepts

### Wanted vs Owned

| Type | Watch for | Triggers |
|---|---|---|
| `WANTED` | Availability, redemption, pending delete | `WANTED_AVAILABLE`, `WANTED_DROPPING` |
| `OWNED` | Expiry, SSL, DNS posture, registrar lock | `OWNED_EXPIRING`, `SSL_EXPIRING`, `SSL_INVALID`, security findings |

### Priority

`HIGH`, `MEDIUM`, and `LOW` control visual weight and are inherited by
generated actions and findings.

### Action Queue

Actions are durable work items generated by status changes. States are
`OPEN`, `SNOOZED`, `DISMISSED`, and `RESOLVED`.

### Security Findings

Owned-domain scans create `risk_findings` from DNS posture and RDAP
registrar-lock signals. Finding states are `OPEN`, `SNOOZED`, `DISMISSED`,
and `RESOLVED`; `SNOOZED` requires a `snoozedUntil` timestamp. The
`/ops/findings` queue supports bulk lifecycle updates, saved
`security-findings` triage views, and keyboard shortcuts for move, select,
reopen, snooze, dismiss, and resolve.

## Architecture

| Layer | Choice |
|---|---|
| Framework | Nuxt 4, Vue 3, Nitro |
| DB | SQLite via Drizzle ORM and better-sqlite3 |
| Styling | Tailwind CSS v4 tokens in `assets/css/main.css` |
| i18n | `@nuxtjs/i18n` with `zh-CN` and `en-US` |
| Scheduling | Built-in timezone-aware scheduler + DB task locks |
| Email | Nodemailer |
| Web Push | `web-push` with VAPID and a hand-rolled service worker |
| RDAP | ICANN RDAP bootstrap discovery |
| CT | crt.sh JSON query for Brand Watch discovery |

## Data Model

| Table | Purpose |
|---|---|
| `domains` | Watch list with `watchKind`, priority, tags, group, and active flag |
| `domain_status_latest` | Latest RDAP snapshot per domain |
| `domain_status_history` | Append-only RDAP history |
| `actions` | Action queue items |
| `notification_rules` | SMTP and email notification settings |
| `notification_events` | Every notification attempt, including retries |
| `app_settings` | Runtime preferences such as cost currency and risk notification presets |
| `audit_logs` | Admin audit stream for login, config, mutations, scans, and review actions |
| `dns_snapshots` | DNS baseline snapshots for owned domains |
| `risk_findings` | DNS/RDAP findings with review lifecycle |
| `brand_watch_terms` | Brand/product/company terms and scan frequency |
| `brand_watch_candidates` | Persisted Brand Watch candidates from RDAP or CT, plus manual review state |
| `webhook_configs` | Outbound webhook destinations |
| `serverchan_configs` | ServerChan SendKey configs |
| `ssl_status_latest` / `ssl_status_history` | SSL certificate snapshots |
| `domain_costs` / `domain_budgets` | Cost ledger and budget schema |
| `push_subscriptions` | Web Push endpoints |
| `saved_filters` | User-saved filter presets |
| `task_locks` / `task_runs` | Scheduling locks and run history |

`brand_watch_candidates.source` identifies the discovery source. `rdap`
means a locally generated candidate was probed through RDAP; `ct` means a
domain was observed in crt.sh Certificate Transparency results. Both store
source details in `evidence_json`. Manual review state is stored separately in
`review_status` so later scans do not overwrite triage decisions.

## Workflows

1. Hourly domain scan runs active domains in batches of five.
2. Each domain scan performs RDAP, SSL checks, and owned-domain DNS security
   probes.
3. Status diffs create or resolve action queue items.
4. Notification fan-out uses email, webhook, ServerChan, and Web Push with
   `Promise.allSettled`, so one channel does not block others. Risk event
   presets can disable individual channels for `SECURITY_FINDING_HIGH` and
   `BRAND_WATCH_REGISTERED`; delivered dedupe keys are summarized from
   `notification_events`, and channel diagnostics explain disabled presets or
   missing SMTP/webhook/ServerChan/push destinations.
5. The Security dashboard aggregates open findings, registrar-lock gaps, DNS
   drift, registered Brand Watch lookalikes, new-in-window trend counts, and
   task-run risk pressure history through `GET /api/security/summary`, then
   links into `/ops/findings` with persisted query filters for triage. Saved
   triage views apply only when the page is opened without query filters.
6. Daily summary runs at 08:00 in `SCHEDULER_TIMEZONE`.
7. Hourly Brand Watch scan processes enabled due terms, generates candidates,
   checks RDAP, queries crt.sh, persists registered or observed lookalikes, and
   emits `BRAND_WATCH_REGISTERED` notifications for newly observed
   registrations.
8. Every task run is recorded in `task_runs` with normalized `riskMetrics`
   when available, while `task_locks` prevents duplicate concurrent jobs.

The scheduler is enabled by default. Set `ENABLE_SCHEDULER=false` to disable
background jobs, and set `SCHEDULER_TIMEZONE` to an IANA timezone such as
`Asia/Shanghai` to control local wall-clock scheduling.

## Brand Watch Boundary

Brand Watch starts from user-configured terms. The app locally generates exact,
typo, prefix/suffix, and aggressive homoglyph candidates. RDAP determines
candidate registration state; crt.sh CT discovery finds observed certificate
names containing the watched term.

The self-hosted edition does not claim full-zone real-time new-registration
discovery. That usually requires privileged zone files or commercial NRD/NXD
feeds.

## Deployment

### Docker

```bash
docker-compose up -d
```

The Docker default serves the app on `http://localhost:8080` and mounts
`./data:/app/data` so SQLite persists on the host.

### Manual

```bash
pnpm install
pnpm exec drizzle-kit push
pnpm build
pnpm preview
```

## Environment Variables

```env
PORT=3000
ADMIN_PASSWORD=
SESSION_SECRET=
SECRET_ENCRYPTION_KEY=
DATABASE_PATH=./data/app.db
BASE_URL=http://localhost:3000

# Explicit opt-outs / deployment controls
# AUTH_DISABLED=true
# TRUST_PROXY_HEADERS=true
# ENABLE_SCHEDULER=false
# SCHEDULER_TIMEZONE=Asia/Shanghai

# Web Push
VAPID_PUBLIC_KEY=
VAPID_PRIVATE_KEY=
VAPID_SUBJECT=mailto:admin@example.com
```

`/api/health` returns only `{ ok, now }` and intentionally does not expose the
database path or other deployment details.
